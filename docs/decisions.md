# 决策记录（ADR）

每条都记录：背景 → 选择 → 理由 → 代价。实现阶段严格按此执行；要改先改这里。

---

## D-01 客户端 Kotlin，服务端 NestJS + TypeScript + PostgreSQL

**背景**：你要求「用 Kotlin 写」，同时明确服务端不用 Python（可用 TS/JS/React/C/汇编）。

**选择**：Android 客户端 Kotlin + Compose；服务端 NestJS 10 + TypeScript；数据库 PostgreSQL 16；ORM Prisma。

**理由**：NestJS 的模块/守卫/拦截器天然适合「三级角色 + 资源归属」这类鉴权；FCM（`firebase-admin`）、阿里云短信（`@alicloud/dysmsapi20170525`）、SMTP（`nodemailer`）都有官方或成熟 Node 库；Postgres 的行锁能直接支撑单实例调度的防重。

**代价**：三种语言（TS/Kotlin/SQL）在一个仓库；NestJS 启动比 Express 重，冷启动约 1–2 秒。

## D-02 邀请码一码一邮箱 + 邮箱验证后才能登录

**背景**：开放注册会让陌生人消耗短信额度；邮箱不验证则无法找回密码，也无法用于 ROOT 告警。

**选择**：管理员生成邀请码时绑定目标邮箱；注册必须邮箱、密码、邀请码三者匹配；注册后 `PENDING_VERIFICATION`，点邮件链接后 `ACTIVE`。

**理由**：邀请码控制入口，邮箱验证控制真实性，两者职责不重叠。

**代价**：多一步邮件配置；邀请码需要管理员手动发。若以后要开放注册，加一个 `registrationOpen` 开关即可（表已预留）。

## D-03 密码用 PBKDF2-HMAC-SHA512 + 随机盐 + 迭代

**背景**：你要求「SHA512 加密后入库，不得明文」。裸 SHA-512（`sha512(password)`）对 GPU 每秒可算数十亿次，配合彩虹表等于明文。

**选择**：`PBKDF2-HMAC-SHA512(password, salt=16B 随机, iterations=210000)`，存 `hash + salt + iterations` 三元组；比较用恒定时比较。

**理由**：仍是 SHA-512 家族，满足你的要求；加盐使彩虹表失效，迭代把爆破成本抬高 5 个数量级；参数可随硬件升级（字段已存 iterations）。

**代价**：单次登录约 100–200ms CPU（可接受）；比 Argon2id 弱，但无需额外原生依赖。

## D-04 JWT：15 分钟 access + 30 天可撤销 refresh

**选择**：access 为 HS256 JWT（`sub`/`role`/`ver`/`jti`），refresh 为 32 字节随机串，库里只存 SHA-256，每次刷新轮换并作废旧值。

**理由**：短 access 缩小泄露窗口；refresh 可撤销解决「封号/改密要立即生效」；不引入 Redis，撤销状态在 Postgres。

**代价**：每次刷新一次 DB 写；多设备各自一条 session。

## D-05 三级角色：ROOT 唯一可转让，ADMIN 管账号不看任务

**选择**：
- ROOT：唯一，不可删除/降级，可转让；唯一能提权/降权。
- ADMIN：建/停用/删普通用户、生成邀请码、改 MemberToken、看系统设置与审计；**看不到他人提醒任务**。
- USER：只有自己的任务与设置。

**理由**：你的最终选择是「仅初始管理员能提权」「管理员看不到他人任务」。取餐码属于个人隐私，管理员只需排障能力（看告警与日志），不需要看别人的取餐码。

**代价**：管理员排障时看不到具体任务，只能看告警与事件计数。若后续需要，可加「用户主动授权管理员查看」的临时授权。

> ⚠️ 与第三轮「管理员可管用户和任务」的措辞冲突，按第六轮结论执行。如要改回，告诉我。

## D-06 MemberToken 加密入库，仅管理员可改

**选择**：单行表 + AES-256-GCM，密钥来自环境变量；接口只回掩码；写入即验证；每次变更写审计；401 时暂停轮询并告警。

**理由**：旧版写 `.env` 明文，容器化后无法热更新且易泄露；加密入库让 DB 备份泄露不等于凭证泄露。

**代价**：密钥丢失则需重新录入凭证（可接受，凭证本来就要定期换）。

## D-07 通知：FCM + ntfy + 短信，短信对已绑定用户必发

**选择**：
- 设备级：有 GMS → FCM；无 GMS → ntfy。
- 用户级：`ntfyEnabled` 可让有 GMS 的用户也开主动连接。
- 短信：`phone` 已验证且 `smsEnabled` → 必发；未绑定 → 不发，App 每次冷启动弹窗提示「只能通过 App/网页查看」。
- 管理员告警：邮件给 ROOT + 站内给全部管理员，不发 ntfy。

**理由**：FCM 在国内网络不可靠、且你现在没有凭据；ntfy 零凭据可用；短信是最后的确定性通道。

**代价**：短信有费用与 20 条/天/号码的硬限制；三套通道需要三套失败处理。

## D-08 ntfy：默认自建，地址可配，每用户一个 topic

**选择**：docker-compose 内起 ntfy；`NTFY_SERVER_URL`（内网 publish）与 `NTFY_PUBLIC_URL`（App 订阅）分离；topic 为 32 hex 随机串；服务端 publish + App 主动 WebSocket 订阅双管齐下。

**理由**：自建可控、不被第三方限流；可配保留迁移自由；双模式让「有 GMS 但想省电」或「无 GMS 但后台被杀」都有兜底。

**实测补充（2026-11-11）**：ntfy **不支持子路径部署**——`NTFY_BASE_URL` 带路径会直接拒绝启动（`base-url must not have a path`）。
最初设计的 `https://域名/ntfy` 方案在实测中崩溃，已改为独立子域 `ntfy.<域名>` + Caddy 第二个站点块。
同时发现 `/me/ntfy/config` 曾把容器内网地址 `http://ntfy:80` 返回给手机（手机不可达），已拆分 `NTFY_PUBLIC_URL`。

**代价**：需要两条 DNS A 记录；App 前台服务常驻有耗电。

## D-09 提醒判定沿用旧版：基线 + 一次性 + 超时

**选择**：首次查询只记基线指纹；仅当「命中且指纹 ≠ 基线」才提醒一次；到 `endsAt` 未命中判 `TIMEOUT` 并通知；查询异常不改主状态。

**理由**：旧版这套逻辑经过实践，能避免把上一单误判为新到；一次性避免重复打扰。

**代价**：若用户在同一柜机用同一取餐码连续两单，第二次不会提醒（指纹相同）。文档里注明。

## D-10 任务三变量与短信三变量分开建模

**选择**：任务 = `pickupCode` / `cabCode` / `durationMin`；短信 = `${cabCode}`（任务）/`${SN}`（全局设备号，管理台可改）/`${box_sn}`（接口返回柜号）。

**理由**：两套变量语义不同，混在一起会导致「用户填的 SN」和「设备 SN」混淆。

**代价**：用户不理解 `${SN}` 时可能疑惑；管理台需给出说明文案。

## D-11 单实例部署，进程内调度（含多实例对比）

**选择**：单实例，`setInterval` + `FOR UPDATE SKIP LOCKED` 防重；不用 Redis。

**优点**
- 零额外中间件：一个 Compose 文件起 Postgres + ntfy + server + caddy，VPS 1C2G 足够。
- 排障简单：所有状态在一个进程、一个数据库里，日志线性。
- 轮询是「每分钟几十次 HTTP」的量级，单实例完全撑得住（单用户 5 任务 × 60s 间隔 = 每分钟 5 次请求）。
- 成本最低：无需 Redis 实例与其运维。

**缺点**
- 进程重启期间（部署/崩溃）轮询中断，任务会漏查几十秒到几分钟——对「外卖入柜提醒」这种分钟级场景可接受。
- 无法水平扩容：两个实例会重复查询、重复发短信。已用 `SKIP LOCKED` 兜底，但仍是「能跑不能扩」。
- 单点故障：服务器挂了就全停。

**何时该切多实例**：用户量到数百、或要求 99.9% 可用时。届时改动点已隔离在 `scheduler/` 一个模块：把「取任务」换成 Redis 队列（BullMQ），`SKIP LOCKED` 换成分布式锁，其余模块不动。**现在不做，是因为它会让部署复杂度翻倍，而收益在这个规模下为零。**

## D-12 数据保留 30 天 / 90 天

**选择**：`Reminder` 与 `ReminderEvent` 保留 30 天；`SmsLog`、`AuditLog` 保留 90 天；每日 03:00 清理。

**理由**：提醒是短生命周期数据，留 30 天足够回看；审计需要更长窗口。

**代价**：超过 30 天的任务不可查（已明确告知用户）。

## D-13 通知内容默认显示柜号+取餐码，可关

**选择**：`showNotifyDetails` 默认 `true`，注册引导页告知可关；关闭后推送只说「外卖到了，打开 App 查看」。短信不受影响（模板固定）。

**理由**：你选了「默认显示，注册时告知」。锁屏可见取餐码有隐私风险，但取餐码本身时效性强、泄露价值低。

---

## D-14 引导页用一次性引导码保护

**选择**：首次启动生成 `XXXX-XXXX` 引导码，写容器日志与 `data/bootstrap-code.txt`；`POST /api/bootstrap` 必须带该码；成功后 ROOT 创建、引导入口永久 404。

**理由**：公网部署下「先到先得」等于把根账号送给扫描器。

**代价**：部署者需要 `docker logs` 或读文件取码（一次性动作）。
